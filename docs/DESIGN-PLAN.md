Status: **plan only, waiting for "ok".** No design-system code has been written. Source of truth: `docs/DESIGN.md`; visual reference: `docs/design-reference/`.

Starting point (v2, done): all five modules, leads, admin, PDFs and emails work on one neutral look with a per-broker accent (`lib/brand/palette.ts`, Tailwind v4 `@theme` tokens in `app/globals.css`). Today 16 files outside the future `src/design/` contain hex colors, 9 reference font names, and 17 use arbitrary `[NNpx]` classes. Those are the migration surface.

## 2. Prisma change

The project uses `prisma db push` (SQLite locally, Postgres on Vercel) and stores enum-like fields as validated strings (status, source, product, etc.), so I'll follow that convention:

```prisma
model Broker {
  theme        String  @default("maison")   // "maison" | "terminal" | "atelier", validated by zod + ThemeId
  accentColor  String  @default("#7D5E22")  // already exists; default changes to the maison brass
  logoOnDarkUrl String?                     // optional logo variant for dark panels (§8 of DESIGN)
}
model Agency {
  defaultTheme String  @default("maison")   // used when the agency creates a broker
}
```

Existing rows get `maison`. Their saved accent is kept if it passes the maison contrast rules, otherwise it snaps to the nearest maison preset and the change is logged in the broker's audit trail. If you want real migration files for production (`prisma migrate` with a baseline), say so and I'll add them in the same step.

Seed: Harborline → **maison** with navy `#1F4E79` (a maison preset), Cactus Ridge → **terminal** with gold `#F4C96B`, Evergreen Key → **atelier** with green `#0B6B4F`. The demo script gets a live theme switch.

## 3. Token contract

DESIGN.md §3.2 as written, plus four additions that the current product needs (otherwise components would hard-code colors or branch on theme):

```ts
export interface ThemeTokens {
  color: {
    bg; surface; surfaceAlt; inverse; onInverse; onInverseMuted; inverseRule;
    ink; ink2; muted; rule; ruleStrong;
    accent; accentText; onAccent; accentTint;          // derived per broker (accent.ts)
    warn; onWarn;
    // + additions
    positive: string;   // cash flow > 0, "Looks strong" text where no block is used (AA on bg/surface)
    negative: string;   // negative cash flow, form errors, destructive actions
    focus: string;      // focus ring (3:1 against bg and surface)
    dim: string;        // terminal chip borders / inactive dots; = rule elsewhere
  };
  font: { display: string; body: string; mono: string };
  type: Record<TypeRole, { size: number; line: number; tracking: number; weight: number; family: "display" | "body" | "mono"; italic?: boolean; upper?: boolean }>;
  //   TypeRole = heroNumeral | dashboardCount | h1 | h1Desktop | section | metric | metricPanel |
  //              optionRate | optionLetter | eyebrow | body | bodySmall | button | fine
  radius: { card: number; tile: number; control: number; cta: number; badge: number; logo: number };
  border: { hairline: number; strong: number };
  space: { page: number; section: number };
  variant: {                                         // read only by the six variant components
    meter: "linear" | "gauge" | "linear-block";
    verdict: "italic" | "chip" | "sentence";
    options: "stacked" | "table" | "sections";
    shell: "sidebar-dark" | "sidebar-bordered" | "topbar";
    icon: { stroke: 1.5 | 2 };
  };
}
```

`design:css` emits one block per theme: `[data-theme="maison"] { --bg: …; --type-hero-size: 132px; … }`. Tailwind v4 maps them (`@theme inline`), so components write `bg-surface text-ink border-rule text-hero` and never see a value. Per-broker accent variables are written inline on the theme wrapper by `ThemeProvider` from `accent.ts`.

## 4. Fonts: only the active theme's families reach the browser

- `src/design/fonts.ts` declares all five families with `next/font/google` (`display: "swap"`, `subsets: ["latin"]`, only the weights in DESIGN §5, `adjustFontFallback` on so swaps don't shift layout) and **`preload: false`** on every one.
- Each theme exports `fontClassNames` (the `.variable` classes of its 2–3 families). `ThemeProvider` puts only those on the `data-theme` wrapper, and the theme's CSS vars point `--font-display/body/mono` at those variables. Browsers download a font file only when a rendered element uses it, so a maison visitor fetches Instrument Serif + Hanken Grotesk and nothing else. The other `@font-face` rules are a few hundred bytes of CSS.
- Then I add back a preload for the active theme's display face only (the LCP numeral) with a `<link rel="preload">` emitted by the theme layout.
- **Verified, not assumed:** a Playwright test loads `/b/<slug>/check` for each theme and asserts the requested `.woff2` files belong only to that theme's families. Lighthouse mobile ≥ 90 per theme is part of the acceptance run. If preload-off hurts LCP, the fallback is one font module per theme imported only in that theme's layout branch; result and choice go in DECISIONS.md.
- PDFs: react-pdf can't use `next/font` or WOFF2. A one-time `design:fonts` step downloads the OFL TTFs (Google Fonts is reachable from here) into `public/fonts/` with their licenses, registered in `src/design/pdf/fonts.ts` (plus Instrument Serif Italic). The current Inter/Fraunces files are removed after the switch.
- Emails: the system fallback stacks are the design; web fonts via `<link>` only as enhancement (Apple Mail).

## 5. Settings → Appearance

New tab in Settings (broker admin; agency admin when impersonating), also step 1 of the onboarding wizard:

1. **Theme cards** (3): name, one-line description, a static thumbnail of the Instant Check hero in that theme. Radio-group semantics, keyboard accessible.
2. **Accent**: the four presets for the selected theme as swatches, plus "Custom" with a hex field. Live readout under the picker: `Text on accent 5.1:1 ✓ · Accent text on background 4.8:1 ✓`. Saving a color that can't reach AA (no `onAccent` option ≥ 4.5:1) is refused with a plain sentence ("White and dark text are both hard to read on this color. Pick a darker or more saturated shade."). `accentText` is derived automatically and shown as a sample.
3. **Logo**: current logo + optional "logo for dark backgrounds" (maison hero, terminal header).
4. **Live preview**: an iframe of `/b/<slug>/check?previewTheme=…&previewAccent=…` at phone width, with tabs for Check / Scenario / Listing / Email. Preview params are honored only for a signed-in user of that broker, the agency, or demo mode; public visitors can't restyle a broker.
5. **Save** applies to every surface at once (public pages, dashboard, PDFs, emails); the change is written to the audit log.

Agency admin: "Default theme for new brokers" on the agency page, and a theme column + override on each broker.

## 6. PDF and email adapters

**PDF**: `getPdfTheme(themeId, accentHex)` returns a frozen plain object in points (px × 0.75): colors, font families, type roles, rules, radii, plus the terminal "paper" variant (light page, dark header band, accent bars with 1px ink outline). PDF documents (`EstimatePdf`, `ScenarioPdf`, `SnapshotPdf`) receive `{ theme, brand, data }` and use only `theme.*` and the PDF primitives. The three structural variants (hero, meter, options) have PDF twins inside `src/design/pdf/components`. QR stays `qrcode` but drawn as SVG paths with a 4-module quiet zone (today it's a PNG data URL). Snapshot must stay one page: shrink gaps, then the photo, then a two-line address; enforced by a test that renders long-address and no-photo fixtures and asserts one page.

**Email**: `getEmailTheme(themeId, accentHex)` returns inline-style objects for the table-based layout (600px). Bars are nested table cells; no SVG; logo and the Equal Housing mark are 2× PNGs (`public/eho.png` rendered at build). Terminal emails are dark, with `bgcolor` attributes, `color-scheme` meta and an Outlook (mso) light fallback. Investor analysis, broker alerts, Money List digest, weekly ROI, realtor stats and scenario notifications all go through the same `EmailShell` + `EmailBrokerFooter`.
